# ADR 0002: Static Framework Linkage for iOS

**Date:** 2026-09-06
**Status:** Accepted

## Context

Until 2026-09-05 no iOS build of this app had ever completed. `pod install` failed outright:

```
The following Swift pods cannot yet be integrated as static libraries:
The Swift pod `FirebaseAuth` depends upon `FirebaseAuthInterop` and
`FirebaseAppCheckInterop`, which do not define modules.
```

React Native Firebase's Swift pods depend on Objective-C pods that emit no module maps. Swift
cannot import those when everything links as a plain static library, which is what CocoaPods
does by default. The linkage mode had to change.

Two constraints shaped the choice.

**`/ios` is generated.** It is gitignored and regenerated by every `npx expo prebuild`, so the
fix the CocoaPods error itself suggests — `use_modular_headers!` in the Podfile — is destroyed
by the next prebuild, and the failure returns with no record of why it was ever fixed. Anything
durable has to go through `app.config.js`, which meant adding `expo-build-properties`.

**Two native SDKs have to coexist in one binary.** This app ships both Firebase and Mapbox.
React Native Firebase's own documentation recommends `useFrameworks: 'dynamic'`, but that
guidance assumes its Swift Package Manager resolution mode. `@rnmapbox/maps` pulls the other
way: `rnmapbox-maps.podspec` carries an explicit branch that detects Expo's precompiled
pipeline (`EXPO_USE_PRECOMPILED_MODULES=1`) and skips its own dynamic-framework flip so that
every Mapbox pod stays consistently static. Its comment is direct about why:

> Expo SDK 56+ precompiled iOS pipeline (prebuilt React core) downgrades every framework-style
> pod back to a static library after the podspec is evaluated. Flipping the Mapbox pods to
> dynamic here fights that and leaves an inconsistent graph.

Dynamic linkage is therefore the one configuration where these two libraries actively
disagree.

## Decision

iOS links as **static frameworks**, configured through `expo-build-properties` in
`app.config.js`:

```js
[
  'expo-build-properties',
  {
    ios: {
      useFrameworks: 'static',
      usePrecompiledModules: false,
      forceStaticLinking: ['RNFBApp', 'RNFBAuth', 'RNFBRemoteConfig', 'RNFBAnalytics'],
    },
  },
],
```

All three settings are load-bearing. Each was added only after the previous one exposed the
next failure, and none of their error messages names this configuration:

- **`useFrameworks: 'static'`** — static *frameworks* define modules, unlike static libraries.
  Without it `pod install` fails.
- **`usePrecompiledModules: false`** — Expo ships prebuilt XCFrameworks for its own modules that
  are not built for static-framework linkage. With them on, the app compiles, installs, and then
  dies at launch under dyld with
  `Symbol not found: ExpoModulesCore.AnyModule._decorateObject`, because `ExpoCamera` resolved a
  different `ExpoModulesCore` than the one bundled.
- **`forceStaticLinking`** — React Native core stays prebuilt regardless, and on RN 0.84+ with
  prebuilt core every React Native Firebase native module must be named here or its headers fail
  `-Werror=non-modular-include-in-framework-module` on `#import <React/RCTBridgeModule.h>`.

## Alternatives Considered

1. **`use_modular_headers!` in `ios/Podfile`** — what the CocoaPods error recommends. Rejected
   because `/ios` is regenerated on every prebuild, so the edit does not survive and leaves no
   trace of the reasoning. `AGENTS.md` forbids hand-editing `/ios` for this reason.

2. **`useFrameworks: 'dynamic'`** — React Native Firebase's documented preference, and the
   correct choice for a project using its SPM resolution. Rejected because `@rnmapbox/maps`
   forces Mapbox pods static under Expo's precompiled pipeline, so dynamic produces the
   inconsistent dependency graph its podspec explicitly guards against. Shipping both SDKs in
   one binary makes their mutual compatibility the deciding factor rather than either library's
   standalone preference.

3. **Opting Firebase out of SPM via `disableSPM: true`** — paired with `forceStaticLinking` in
   React Native Firebase's documentation. Not applicable here: `@react-native-firebase/app` is
   pinned at 25.1.0, which has no SPM support and no such plugin option; the string appears
   nowhere in the package. Revisit if the package is upgraded, since SPM is its stated direction
   and CocoaPods support for the Firebase Apple SDK is deprecated after October 2026.

## Consequences

**iOS builds work.** That is new. Verified 2026-09-05 by a clean
`expo prebuild --clean` → `pod install` → build → launch cycle on the simulator, with the JS
bundle loading and the app reaching `200 GET /ganaps` against the dev API.

**Full rebuilds are slower.** `usePrecompiledModules: false` means Expo's modules compile from
source rather than arriving prebuilt — the pod count roughly doubles as source pods replace
XCFrameworks. Incremental rebuilds still hit derived data and are unaffected. This cost is
accepted in exchange for a binary that launches.

**`forceStaticLinking` is a list that must be maintained.** Adding a React Native Firebase
module without adding its pod name breaks the build with an error that points at a header, not
at this list. Keep it in sync with the `RNFB*` entries in `ios/Podfile.lock`.

**The three settings are a set.** Removing any one reintroduces a distinct failure, one of which
(the dyld symbol mismatch) appears only at launch and not at build time. `AGENTS.md` carries the
operational version of this under *iOS Native Build Configuration*.

**Flipper must stay out of the dependency graph** — `use_frameworks!` is incompatible with it.
It is not currently a dependency.

**Binary size and launch time shift with linkage mode** and have not been measured. Worth doing
before the first TestFlight upload, since download size feeds App Store limits.
